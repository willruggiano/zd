# Domain documentation

This project has one domain context.

Before design, implementation or review, read these documents:
1. [The glossary](../../GLOSSARY.md).
2. [The ADRs](../adr/) that apply to the change.
3. The applicable spec or ticket.

Use glossary terms consistently in code, tests, tickets and discussion.
Keep glossary definitions about the domain, not implementation details.

If a change conflicts with an existing ADR, report the conflict before you continue.
Agree on a revised decision. Do not silently replace the existing decision.
